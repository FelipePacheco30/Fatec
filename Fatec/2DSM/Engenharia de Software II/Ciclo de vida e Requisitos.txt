Ciclo de Vida do Software

Cada tipo de aplicação tem preocupações específicas:
- Web: problemas relacionados a rede, hospedagem, escalabilidade.
- Mobile: dependência do sistema operacional, compatibilidade com dispositivos.
- Desktop: uso de memória RAM, espaço em disco e desempenho local.

O projeto geralmente começa pelo banco de dados, pois a modelagem de dados influencia a interface, as regras de negócio e outros elementos.

O Product Owner (PO) é crucial no desenvolvimento:
- Uma elicitação de requisitos mal feita pode comprometer todo o projeto.

-------------------------------------
Levantamento e Análise de Requisitos

Objetivo: definir O QUE FAZER.
- Levantar requisitos.
- Quebrar em tarefas (tasks).
- Definir responsáveis.

Tipos de Requisitos:
- Funcionais: funcionalidades do sistema (features).
  Exemplo: “Cadastrar Cliente” vira uma funcionalidade implementada.
- Não funcionais: condições para que os requisitos funcionais sejam atendidos.
  Exemplo: desempenho, segurança, usabilidade.
- Importante: não existe requisito “semi-atendido”. Ou é atendido ou não é.

Regras de Negócio:
- Variam de acordo com o objetivo e cliente.
- Exemplo: Sistema de padaria ≠ Sistema educacional (dados e processos diferentes).

-------------------------------------
Modelagem

Objetivo: organizar requisitos de forma visual para melhor entendimento.
- Casos de uso: mostram o que o sistema pode fazer e quem interage com ele.
- Classes: descrevem atributos e métodos dos objetos do sistema.
- Diagramas de sequência: descrevem passo a passo como ocorre a interação entre objetos.
  Exemplo: acessar tela de cadastro → fornecer dados → clicar em botão.

-------------------------------------
Implementação

- Transformar a modelagem em código.
- Boa prática: associar tarefas a User Stories, facilitando organização e controle.

-------------------------------------
Testes e Validações

- Objetivo: verificar se o que foi implementado atende aos requisitos.
- Tipos de teste: unitários, integração, aceitação.
- É necessário documentar os testes realizados.

Diferença entre Verificação e Validação:
- Verificação: checagem se tudo que foi feito está de acordo com o planejado. Pode ser feita por qualquer pessoa da equipe (check-list).
- Validação: aceite do requisito pelo PO (Product Owner). Só ele pode validar, explicando porque está correto. Uma tarefa só está pronta quando está validada.

-------------------------------------
Implantação

- Colocar o software em ambiente de produção (rodar de forma real).

-------------------------------------
Manutenção

- Manter o sistema funcionando e atualizado.
- Quando fica obsoleto, pode ser desativado e substituído.

-------------------------------------
Boas Práticas e Referências

- Associar tarefas a User Stories.
- Ler “UML 2 – Uma Abordagem Prática”.
- Ler “Código Limpo” (Clean Code).
